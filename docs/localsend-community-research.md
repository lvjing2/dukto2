# LocalSend 社区需求与 dukto2 独立方向评估

调研日期：2026 年 10 月 18 日。功能开发暂停，dukto2 保留 `checkpoint-0.1.1-2026-10-18`。

**大文件中断恢复存在真实需求，值得开展有限验证；目前还不足以证明需要长期维护一个独立的通用传文件应用。** 最有价值的候选定位是：让普通用户在 macOS 与 Android 之间传输大文件或大批文件时，中断后能够继续，并明确知道哪些文件已完整保存。Android 后台服务、直接保存、换一套界面和使用新框架，都不足以支撑这个定位。

## 需求证据与当前进展

以下状态是本次读取时的 GitHub 状态。报告日期、使用版本和实际故障时间分别标明；Open 表示议题仍开放，不等于当前正式版已复现。点赞仅用于判断有人关注，不用于推算用户规模。

| 需求 | 用户实际场景 | 状态与证据强度 | 对 dukto2 的意义 |
| --- | --- | --- | --- |
| 单个文件或任务中断后继续 | [#1191](https://github.com/localsend/localsend/issues/1191) 于 2024 年提出；不同用户随后报告 30GB 数据传到一半中断、5GB 文件因中断无法完成 | Open，13 个赞，4 条评论；具体故障描述来自旧版本时期，版本未注明。与当前 v2 上传实现缺少偏移恢复相互印证 | 核心候选需求；不能仅修复某一种断线原因 |
| 批量任务只补失败文件 | [#3418](https://github.com/localsend/localsend/issues/3418)，2026-09-10：118GB、307 个文件，只剩 7 个失败，却难以定位和重试；另一个用户称最后借助 rsync 补齐并校验 | Open；报告明确使用 **1.17.0**，虽发表于 1.18.2 发布后，仍不能当作 1.18.2 复现结果 | 真实工作流痛点。失败筛选、可复制路径和批量重试可先贡献上游 |
| 超时后自动补传失败项 | [#2934](https://github.com/localsend/localsend/issues/2934)，2026-02-10：Windows → Android 平板，4GB 文件夹，休眠后出现大量超时，逐项点击重试很繁琐 | Open；版本未注明，早于 1.18 的后台服务改进 | 证明批量恢复需求，不能直接证明单文件字节续传需求 |
| 重发文件夹跳过已完成项 | [#2127](https://github.com/localsend/localsend/issues/2127) 与 [#2824](https://github.com/localsend/localsend/issues/2824)：重复发送大目录浪费时间和空间，希望记录完成状态 | 均 Open；#2127 有 12 个赞。已有 [PR #3202](https://github.com/localsend/localsend/pull/3202)，仍 Open，按大小与修改时间跳过文件，明确排除字节续传，SAF 目录尚不覆盖 | 上游已有具体工作，避免重复做同一个补丁；元数据相同不代表内容经过核验 |
| 大文件准备时应用无响应 | [#3556](https://github.com/localsend/localsend/issues/3556)，2026-10-08：Samsung S20、Android **1.18.2**，选择 16GB 文件后反复出现“等待”提示，数分钟后才开始；发送期间也出现提示 | Open，无评论；是当前版本的具体报告。标题写崩溃，正文主要描述无响应，不能断言根因或普遍性 | 大文件体验仍有缺口；需分开测量选文件、准备、校验和传输，不能把“使用 Rust”视作自动解决 |
| 成功状态与实际文件一致 | [#3441](https://github.com/localsend/localsend/issues/3441)，2026-09-16：Android → Mac，双方 **1.18.2**，用户称发送端报成功，但接收端有 0KB 或缺失媒体，重试产生带编号副本 | Open，无评论；未有维护者确认根因。报告的 macOS 名称与版本号自相矛盾，不能精确推断系统范围 | 值得把完成回执与实际落盘校验纳入验收；不能据此声称 LocalSend 普遍损坏文件或没有校验 |
| 磁盘满后提示并继续 | [#2440](https://github.com/localsend/localsend/issues/2440)：手机 → PC，磁盘满后清理空间仍不继续；2026 年有其他用户附和，并希望发送端解释原因 | Open；没有明确当前版本的复现 | 属于同一恢复流程的后续场景；仅增加“磁盘空间不足”提示适合上游修复 |
| 大量照片容易选择和补齐 | [讨论 #3389](https://github.com/localsend/localsend/discussions/3389)，2026-08-31：7000 多张照片，用户受每批 999 张及反复滚动影响，希望按范围、日期和相册选择 | Unanswered，0 回复；版本未注明，999 是该用户遇到的限制，不能概括所有平台 | 真实但目前样本小；选择器改进更适合先贡献上游。照片整理与备份会扩大产品范围 |

## 已解决或已有方案的需求

**Android 传输期间保持后台运行已有正式实现。** [#2805](https://github.com/localsend/localsend/issues/2805) 于 2026-10-06 被成员以 completed 关闭，明确指向 1.18.0 的前台服务实现。前台服务减少中断的机会，不能代替断点续传，也不代表系统永远不会结束进程。不能继续用旧版息屏掉线报告证明当前版本缺少后台服务。

**直接保存到文件夹已有可用设置。** [#3153](https://github.com/localsend/localsend/issues/3153) 的报告者在关闭“保存媒体到图库”、选择接收文件夹后，亲自确认文件直接写入目标，随后关闭议题。这不意味着所有图库或文档提供程序路径都没有临时副本；它意味着“LocalSend 一律需要双倍空间”不成立。

正式版 [v1.18.2](https://github.com/localsend/localsend/releases/tag/v1.18.2) 也已包含代理处理、应用恢复时 HTTP / 组播监听器重建等修复。监听器重新启动与未完成文件继续写入是不同能力。2023 至 2024 年的大文件崩溃、图片批量卡死等报告，不能未经新版本复现就计入当前缺口。

## 断点续传目前缺在哪里

本次 `releases/latest` 仍指向 v1.18.2。源码固定到正式标签 `af0416be50770a97760f7070684bc667b759a15c`，并核对远程 main 仍为本地参考的 `d01fdb14c978fa8b2b13e29a50cc0feaefe5c1b9`。

| 恢复层次 | 实际含义 | 本次证据 |
| --- | --- | --- |
| 批量补传 | 300 个文件完成，7 个失败，只重新发送这 7 个 | 已有逐文件重试，但社区要求更方便、更可靠的批量补传与去重；#3202 在处理其中一部分 |
| 单文件字节续传 | 一个 20GB 文件已收到 15GB，重新连接后从已核验位置继续 | v1.18.2 的 v2 上传没有恢复偏移协商；现有校验失败重试重新上传整文件 |
| 进程重启后续传 | 任一端关闭后重开，找回任务、文件访问权限和可信接收进度 | 当前会话为内存状态，没有持久化的已核验字节进度。它是候选产品的工程目标，社区样本尚未证明用户对这一层的需求频次 |

源码依据是 [v2 客户端上传](https://github.com/localsend/localsend/blob/v1.18.2/packages/core/src/http/client/v2.rs)、[会话结构](https://github.com/localsend/localsend/blob/v1.18.2/packages/core/src/http/server/common/session.rs)、[保存实现](https://github.com/localsend/localsend/blob/v1.18.2/packages/core/src/http/server/common/save.rs) 和 [Android 重开保存目标](https://github.com/localsend/localsend/blob/v1.18.2/packages/localsend_isolates/lib/src/task/server/file_saver.dart)。上传参数为 sessionId、fileId、token；普通路径创建目标文件，Android 重试重开使用截断写入。应用选择的仍是 v2 客户端。这些证据支持“检查的原生传输路径没有字节断点续传”，不能扩大为所有第三方客户端或未来版本的结论。

LocalSend 已支持 SHA-256 校验，默认启用；校验与续传是不同能力。[路线图中维护者于 2026 年 8 月 5 日的更新说明](https://github.com/localsend/localsend/issues/345) 列出校验、后台传输、CLI 和性能改进。#3441 的用户报告需要继续调查，不能倒推出完全没有完整性检查。

**上游并未拒绝续传。** [协议议题 #31](https://github.com/localsend/protocol/issues/31) 提议改为支持 Range 的下载端点，也提到 tus。维护者回应了现有上传方向的防火墙理由：发送方发起连接时，只需接收方开放入站；改成下载会反转连接发起方向。该提案仍 Open，没有发布计划承诺。现有 v3 文件主要涉及身份交互，不能因目录名包含 v3 就认为续传已落地。

对公开 PR 的定向检索未发现已实现完整字节续传的 PR；#3202 明确将其作为另一项协议改动。检索结果不能证明无人正在开发，也不能预测上游合入时间。

## 其他需求是否更适合独立做

| 方向 | 社区证据 | 判断 |
| --- | --- | --- |
| 无路由器时直接连接 | [Wi-Fi Direct #189](https://github.com/localsend/localsend/issues/189) 63 个赞，[Wi-Fi Aware #2523](https://github.com/localsend/localsend/issues/2523) 41 个赞；有人愿意赞助，维护者明确表示 Wi-Fi Aware 已计划 | 关注度高于本次续传议题，但平台连接层投入大，且上游已有方向。暂不作为 macOS / Android 初期切入点 |
| VPN 内自动发现 | [Tailscale #1123](https://github.com/localsend/localsend/issues/1123) 33 个赞；用户手填 IP 可用，希望自动发现 | 需求真实，已有手动地址等绕行方式；需要扩展远程网络与信任范围。当前仍以局域网为边界 |
| 失败筛选、重试全部、选择照片 | #3418、#2934、讨论 #3389 | 适合小范围上游贡献，单项不足以支撑另一套协议与多平台维护 |
| 可恢复的大文件任务 | #1191、#2127、#2824，加上当前版本的大文件与完成状态报告 | 最贴近 dukto2 现有范围，值得验证。优势必须来自端到端完成体验及验证结果 |

点赞数截至调研时，只能横向观察关注，不能把不同年份、不同议题的数值相加。Wi-Fi Direct 和 Wi-Fi Aware 也不能视作跨平台完全等价的技术。

## dukto2 的候选定位与成本

候选定位：**面向普通用户的局域网大文件传输，连接中断后能继续，失败项能补齐，完成结果可核验。** 先聚焦 macOS 与 Android 上 10GB 以上视频、镜像或素材搬运。多文件夹恢复可以作为后续扩展；不立即扩大到同步、图库备份或跨互联网。

这一定位成立需要同时处理四件事：

1. 持久化任务与已经可靠写入的进度，区分接收字节、落盘字节和已校验字节。网络重连后协商恢复位置，而不是只在界面恢复百分比。
2. 识别同一个可信设备及同一个版本的源文件，拒绝把修改后的源文件或损坏的局部内容拼接起来。仅按名称、大小或 IP 识别不足以保证安全恢复。
3. 处理 Android 的文件 URI 授权和保存目标。部分提供程序无法随机读写或持久授权，必须明确能力边界及重新授权流程，不能承诺任意目录都可续传。
4. 按实际校验和保存结果给出完成回执；重连查询已提交结果，避免“对方已保存但回执丢失”导致重复文件。失败原因和可恢复操作必须在界面中清楚表达。

这需要改动现有协议与存储生命周期。dukto2 当前会在中断及启动时清理未提交数据，没有持久化续传；前台服务和直接保存只是基础能力。既有 4GiB 核心同机测试也不能证明 Android 大文件、应用重启恢复或相对 LocalSend 的优势。当前边界见 [可靠性与验证记录](reliability.md)。

## 下一步决策条件

继续暂停功能扩张。先按下面的对照验收表，在同一 Mac、Android、网络和保存目录条件下记录正式 LocalSend 1.18.2 的行为；不关闭 TLS 来换取通过。这里是验证建议，本轮没有执行设备实验。

| 场景 | 要记录的事实 | dukto2 若独立继续应达到的目标 |
| --- | --- | --- |
| 双向传输真实 20GB 单文件，在 30% 和 90% 断开 Wi-Fi 再连接 | 错误、恢复操作、重发字节数、耗时、最终摘要 | 从已核验位置恢复；重发量不超过预先公布的检查点窗口 |
| 传输中关闭进程，再打开；另测用户强行停止后手动重开 | 任务是否保留、文件权限是否仍可用、是否需要重新选择源文件 | 在声明支持的本地存储目标上恢复，不能自动启动时明确提示；不承诺 Android 强行停止后后台自行复活 |
| 息屏和退后台分别持续 30 分钟 | 进度是否持续，若中断能否恢复，是否影响系统操作 | 大文件传输不中断界面操作；系统结束进程后仍可找回任务 |
| 接收磁盘满后释放空间；恢复前修改源文件 | 两端错误提示、局部文件处理、完整性结果 | 可解释、可恢复；源内容变化时拒绝错误拼接 |
| 完成前后中断回执；再发送同一任务 | 双方状态、最终文件数、重复文件和摘要 | 已提交状态可查询，不假报成功，不因自动重试覆盖用户文件 |
| 后续扩展到 100GB 混合文件夹，部分文件故意失败 | 成功清单、失败筛选、只补失败项、重复情况 | 已完成文件不重传，失败项可一次补齐；与单文件续传分开验收 |

独立投入的门槛建议为：找到 3 至 5 位经常搬运大文件、愿意实际使用的测试者；确认他们在当前版本与现有工具中仍有反复发生的恢复成本；在一至两个最重要场景上证明无需重新从头发送且操作足够简单。这个人数是验证范围建议，不是现有社区统计，也不代表市场规模。

如果验证只剩失败列表、重试按钮或选文件体验的问题，优先贡献 LocalSend。如果用户明确需要可持久恢复的任务，并愿意为此选择 dukto2，则先做范围受控的恢复原型，再决定是否作为独立产品长期维护。未来 LocalSend 补齐这一体验时，也应重新评估独立维护的必要性。

本轮证据来自公开 GitHub 议题、讨论、PR、正式发布和固定源码，不包含私有社区或用户访谈。未实际运行 LocalSend，不据此宣称 dukto2 更快、更省内存或更可靠。核心公开 JSON 快照保留在本地忽略目录 `artifacts/research/community-2026-10-18/`，报告链接可直接追溯原始讨论。
